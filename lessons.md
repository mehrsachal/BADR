# BADR Lessons Learnt & Memory

- Always check if the Coordinate Reference System (CRS) of multiple layers matches before performing geometric operations like Buffer, Clip, or Slope to ensure spatial accuracy.
- When generating Python scripts for QGIS, prefer using the `processing` module for complex workflows as it handles many edge cases automatically.
- For heatmap/KDE visualizations, do NOT use domain-specific fixed distances (e.g. 500m proximity zones, safety buffer radii) as the kernel radius. Instead, scale the radius to the spatial extent of the input points (~10-20% of the bounding-box diagonal) so the output shows regional spread/concentration. Fixed distances are for buffers/zones, not density visualization.
- The 'gdal:rastercalculator' processing algorithm can silently fail to write its output on Windows (reports success but file is missing). For simple raster threshold/math operations, prefer using the GDAL Python API directly (gdal.Open + numpy + driver.Create) or QGIS's native 'qgis:rastercalculator' / 'native:rastercalc' as a more reliable alternative.
- When calculating slope from a DEM in geographic CRS (EPSG:4326), always reproject to a projected CRS (like UTM) first. Slope calculations on geographic coordinates produce wildly incorrect results because pixel dimensions are in degrees, not meters.
- For rasterizing complex scanned maps based on a legend, do not attempt to map colors programmatically; instead, use Supervised Classification (ROI training) to map unique color signatures to integer class values.
- Always auto convert to Porjected CRS if needed for an anlysis tool
- Always explicitly set the Coordinate Reference System (CRS) when creating new vector layers using QgsVectorFileWriter to avoid 'layer has no CRS' errors. Use the source layer's CRS to ensure alignment.
- GRs (Grid References) in this context refer specifically to geographic coordinates (Latitude, Longitude) in EPSG:4326. For Indian Grid or other projected coordinate system requirements, coordinate transformation to the relevant UTM or specific Indian Grid zone (e.g., EPSG:24378 for India Zone II) must be explicitly performed using QgsCoordinateTransform.
- When creating Voronoi polygons for a specific area, the native:voronoipolygons algorithm relies on the input points' extent for its internal buffer. If the result is incomplete, simply using a large 'BUFFER' parameter is insufficient; instead, it is best practice to generate Voronoi polygons from a set of points that includes the corners of the target boundary's bounding box, or to use a significantly larger artificial buffer, and finally clip the resulting polygons to the target boundary to ensure full coverage.
- For network analysis and routing operations in QGIS, do NOT import classes like QgsGraphBuilder, QgsGraph, QgsGraphDirector, or QgsVectorLayerDirector from qgis.core. They must be imported from qgis.analysis (e.g., `from qgis.analysis import QgsGraphBuilder, QgsVectorLayerDirector`).
- In QGIS network analysis (PyQGIS), the strategy classes are named `QgsNetworkDistanceStrategy` (for distance-based cost) and `QgsNetworkSpeedStrategy` (for speed-based cost). There is no class named `QgsDistanceStrategy` (which results in an `ImportError`). Always use `QgsNetworkDistanceStrategy` when building a graph director.
- When initializing `QgsVectorLayerDirector`, the 6th argument (default direction) must be an explicit `QgsVectorLayerDirector.Direction` enum member (e.g., `QgsVectorLayerDirector.DirectionBoth`, `QgsVectorLayerDirector.DirectionForward`, or `QgsVectorLayerDirector.DirectionBackward`). Do NOT pass raw integers (like `2`, `0`, or `1`), as this will cause a `TypeError: argument 6 has unexpected type 'int'`.
- When calculating distances or creating buffers (e.g., 20km reach), ALWAYS ensure the layer is in a projected coordinate system (like UTM) in meters. Performing these operations on geographic coordinates (like EPSG:4326) calculates distances in degrees, leading to massive spatial errors and distorted shapes. Always reproject to a local UTM zone first.
